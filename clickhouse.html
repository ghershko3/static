01How it works
Three core concepts explain almost everything about ClickHouse performance.
Concept 1 of 3
Every INSERT creates a new "part"
ClickHouse never writes to existing data. Each insert creates a brand-new part — a folder on disk with one compressed file per column, sorted by your primary key. It's immutable the moment it's written.
📁
Analogy: Imagine instead of updating a spreadsheet, you make a new copy of it every time. Then someone quietly merges the copies in the background. That's exactly what ClickHouse does.
What's inside a part?
1
column_name.bin — one per column
Each column is compressed and stored separately. A query that only needs 3 columns reads only 3 files — not the entire row.
2
primary.idx — the sparse index
One index entry per 8,192 rows (called a granule). Much smaller than a row-level index. Used to skip entire blocks of data.
3
minmax_*.idx — partition pruning index
Stores the min and max value of partition columns per part. Used to skip entire partitions before even checking the primary index.
Concept 2 of 3
Background merges keep things healthy
ClickHouse runs merge workers 24/7. They pick up small parts, sort and combine them into one large part, then delete the originals. Fewer parts = smaller index = faster queries.
The merge cycle
→

🚨 Breaking point

⚠️
The danger: if you insert millions of tiny batches (1 row per insert), you create millions of parts. Merge can't keep up. ClickHouse throws "too many parts" and stops accepting inserts. Always insert large batches — at least 10,000 rows at a time.
Concept 3 of 3
Columnar storage = only read what you need
Traditional databases store one row at a time on disk. ClickHouse stores one column at a time. If your query touches 3 out of 100 columns, ClickHouse reads roughly 3% of the data.
Row store (PostgreSQL, MySQL)
To get SELECT name FROM users, it reads every row — including all the columns you didn't ask for.
Column store (ClickHouse)
To get SELECT name FROM users, it opens only name.bin. Every other column file is untouched.
-- Check your part health SELECT partition, count() parts, formatReadableSize(sum(bytes_on_disk)) size FROM system.parts WHERE table = 'your_table' AND active = 1 GROUP BY partition ORDER BY parts DESC;
02Mutations
Why UPDATE is painful — the biggest gotcha for people coming from MySQL or PostgreSQL.
The problem: parts are immutable
Because ClickHouse never edits existing data, running ALTER TABLE … UPDATE or DELETE can't just change a few bytes. It has to rewrite every affected part from scratch — decompress → modify → sort → compress → write new files → delete old files.
📚
Analogy: Imagine you have 1,000 printed books and you need to change one word on page 50. You can't erase it — so you reprint all 1,000 books. That's what a mutation does. On 500 GB of data, this takes hours.
What makes it worse
1
New inserts during a mutation extend the queue
Parts created after the mutation started also need rewriting. If you're inserting fast enough, the mutation never catches up.
2
Disk usage temporarily doubles
Old and new versions of every part coexist until cleanup. Make sure you have 2× disk headroom before running a large mutation.
3
CPU spikes
All that decompression and recompression is CPU-heavy. It competes with your read queries.
Monitor mutations
Check parts_to_do — if it's not shrinking for 30+ minutes, the mutation is either stuck or chasing new inserts.
The real fix
Design your table to not need mutations. ReplacingMergeTree handles upserts at merge time — no rewrites, no drama.
-- See what's running SELECT table, command, parts_to_do, parts_done, latest_fail_reason FROM system.mutations WHERE is_done = 0; -- Kill a stuck mutation KILL MUTATION WHERE mutation_id = 'mutation_4.txt';
03Engine families
The engine determines how data is stored and what happens at merge time. Most tables use MergeTree or one of its variants.
MergeTreeUse this by default
Append-only events — logs, clicks, metrics, sensor data
The base engine. Data is sorted by your primary key, stored in immutable parts, merged in the background. No deduplication — every row you insert stays forever.
Use whenYour data is events that don't change — web logs, financial ticks, IoT sensors, analytics events. The vast majority of ClickHouse tables are plain MergeTree.
▶ Show variants (ReplacingMergeTree, SummingMergeTree, AggregatingMergeTree, CollapsingMergeTree)
ReplacingMergeTreeAt merge time, keeps only the latest row per primary key. Use this instead of ALTER UPDATE mutations for upsert patterns. Important: duplicates are visible until a merge runs. Add FINAL to your SELECT to force deduplication at read time: SELECT … FROM t FINAL.
SummingMergeTreeAt merge time, sums numeric columns for rows with the same primary key. Perfect for pre-aggregated counters like daily page views or revenue totals — no need to GROUP BY at query time.
AggregatingMergeTreeLike SummingMergeTree but for any aggregate function, not just SUM. Used with Materialized Views to keep running aggregates updated as data lands.
CollapsingMergeTreeUses a sign column (+1 or −1). Insert +1 to "add" a row, −1 to "cancel" it. At merge time, paired rows cancel out. Lets you update mutable state without ever running a mutation.
Integration enginesExternal data
Query Kafka, S3, MySQL, PostgreSQL as if they were ClickHouse tables
No ETL pipeline needed. Data is fetched live from the external source at query time, or in the case of Kafka, consumed in a background stream.
Use whenIngesting a Kafka stream in real time, or querying files sitting in S3 without loading them first.
▶ Show integrations (Kafka, S3, MySQL/PostgreSQL)
KafkaConsumes a Kafka topic. Always pair it with a Materialized View that writes to a MergeTree table — otherwise consumed messages aren't stored anywhere.
S3 / S3QueueQuery Parquet, CSV, or JSON files in S3 directly. S3Queue watches a prefix and auto-ingests new files as they land.
MySQL / PostgreSQLRead/write pass-through to an external database. Useful for joining live transactional data with ClickHouse analytics.
BufferUtility
Server-side batching layer to absorb insert storms
Holds incoming writes in RAM and flushes them to a target MergeTree table in batches based on time or row count thresholds. Invisible to your application.
Use whenYou can't batch on the client side — e.g. many microservices each inserting 1 row — and parts are piling up. Buffer is the server-side fix.
Distributed + ReplicatedMergeTree Cluster
Multi-shard, multi-replica ClickHouse clusters
Distributed is a virtual table that fans queries out to all shards and merges results. Your app queries Distributed; data lives in MergeTree tables on each shard.

ReplicatedMergeTree is any MergeTree engine with a Replicated prefix. Replicas coordinate via ZooKeeper — inserts land on one replica and propagate to others in the background.
Use whenYour data is too large for one server (sharding) or you need high availability with automatic failover (replication).
04Keys, sorting & rules
The three settings that most affect query performance — and the rules you'll wish someone told you earlier.
ORDER BY vs PRIMARY KEY vs PARTITION BY — what's the difference?
O
ORDER BY — how rows are physically sorted on disk within each part. This is the most important setting. The primary index is built from these columns. Match it to your most common WHERE and GROUP BY columns.
Example: ORDER BY (date, user_id) makes filtering by date very fast. Filtering only by user_id will be a full scan.
P
PRIMARY KEY — the columns used to build the sparse index. Defaults to the same as ORDER BY. You can set it to fewer columns than ORDER BY, but you rarely need to.
The index has one entry per 8,192 rows, not one per row. It skips entire blocks, not individual rows.
↕
PARTITION BY — splits data into separate folders by value (e.g. by month). ClickHouse can skip entire partitions before even checking the index.
⚠️ Don't over-partition. Each partition has its own set of parts. Partition by month, not by user_id.
Rules that will save you in production
✓
Put time first in ORDER BY. Almost all analytics filter by time. ORDER BY (date, user_id) not (user_id, date).
✗
Don't partition by high-cardinality columns. PARTITION BY user_id creates millions of tiny partitions — each with its own parts. Use toYYYYMM(date).
✓
Batch inserts — minimum 10,000 rows per call. Aim for 100k–1M. Use a queue, a Buffer engine, or client-side batching. Never insert one row at a time.
✗
Never use SELECT *. ClickHouse reads only the columns you ask for. SELECT * opens every single column file — destroying the columnar advantage.
✓
Use ReplacingMergeTree instead of ALTER UPDATE. Mutations rewrite entire parts and can run for hours. ReplacingMergeTree handles deduplication cheaply at merge time.
✗
Don't JOIN with large tables on the right side. ClickHouse loads the right-side table entirely into memory. Use Dictionaries for dimension lookups instead.
05Detecting & fixing problems
All ClickHouse health signals live in the system database. These are the tables you'll use most.
TableWhat it tells youAlarm & fix
system.parts Every part on disk — size, rows, partition, age >100/partition
Fix: reduce insert frequency or add a Buffer engine
system.mutations parts_to_do not shrinking = stuck mutation stuck >1h
Fix: KILL MUTATION WHERE …
system.merges Active background merges and their progress queue >50
Fix: reduce insert rate, check CPU
