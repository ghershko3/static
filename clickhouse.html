01

How writes work

Every INSERT = a new part
ClickHouse never edits existing data. Each insert creates a new sorted, immutable, compressed directory on disk instantly.
Tiny inserts = disaster
1 row per insert = 1 part. Above ~300 parts per partition ClickHouse refuses new inserts with "too many parts."
-- Good: one large batch INSERT INTO events SELECT * FROM staging; -- Bad: loop inserting one row at a time
What's inside a part?
A folder with one .bin compressed file per column, a primary.idx sparse index (one entry per 8,192 rows), and minmax index files. ClickHouse reads only the columns your query needs — that's why it's fast.
02

Parts & merges

The merge loop
Background workers merge small parts into large ones 24/7. The sparse index has one entry per 8,192 rows — queries skip entire blocks of data that can't match. Fewer parts = smaller index = faster scans.
Healthy
<100 / partition

Merge keeps up. Queries skip most parts via the index.
Breaking point
100–300 queries slow

>300 inserts fail
SELECT partition, count() parts, formatReadableSize(sum(bytes_on_disk)) size FROM system.parts WHERE table = 'your_table' AND active = 1 GROUP BY partition ORDER BY parts DESC;
03

Mutations

ALTER UPDATE / DELETE = full rewrite
Parts are immutable. So ALTER TABLE … UPDATE schedules a background job that reads every affected part, decompresses it, applies your change, re-sorts, re-compresses, and writes new files. On 500 GB this takes hours. New inserts during the mutation create new parts that also need rewriting.
Side effects
Old + new parts coexist until cleanup. Disk usage temporarily doubles. CPU spikes during the rewrite.
The right fix
Use ReplacingMergeTree for upserts — the engine deduplicates at merge time, no painful rewrites needed.
SELECT table, parts_to_do, parts_done, latest_fail_reason FROM system.mutations WHERE is_done = 0;

Engine families

Four families cover 99% of real use cases. Pick by what your data looks like and how you query it.

MergeTreeDefault choice
Append-only analytics — events, logs, metrics
Base engine. Data sorted by primary key, immutable parts, background merges. No deduplication.
Use whenInserting events that never change — clickstream, logs, sensor data, financial ticks.
ReplacingMergeTreeDeduplicates on primary key at merge time. Use for upserts instead of mutations. Add FINAL to queries to force dedup at read time.

05

Deep dive

Primary key index
Sparse
One entry per 8,192 rows. Marks the min value of the first key column per block. Skips entire blocks, not individual rows.
Granule size
8,192 rows
Smallest unit ClickHouse reads. Even a 1-row query decompresses a full granule. Tune with index_granularity.
Compression
LZ4 default
Each column compressed independently. Similar values sit together = much better ratios than row stores. Switch to ZSTD for higher compression at CPU cost.
Replication
ZooKeeper
Add Replicated prefix to any MergeTree. Replicas coordinate via ZooKeeper. Each merges independently.
PRIMARY KEY vs ORDER BY vs PARTITION BY
O
ORDER BY — how rows are physically sorted within each part. The most important setting. Match it to your most common WHERE / GROUP BY columns.
P
PRIMARY KEY — columns used to build the sparse index. Defaults to ORDER BY. Controls which granules get skipped.
P
PARTITION BY — splits data into separate directories by value (e.g. month). Entire partitions can be skipped. Don't over-partition — too many partitions = too many parts.
Production rules
✓
Put time first in ORDER BY. Most analytical queries filter by date range. ORDER BY (date, user_id) not (user_id, date).
✗
Don't partition by high-cardinality columns. PARTITION BY user_id creates millions of tiny partitions. Use toYYYYMM(date).
✓
Batch inserts. At least 100k–1M rows per call. Use a queue, Buffer engine, or client-side batching.
✗
Avoid SELECT *. ClickHouse reads only requested columns — SELECT * destroys the columnar advantage.
✗
Don't JOIN large right-side tables. ClickHouse loads the right side into memory. Use Dictionaries or denormalize instead.
